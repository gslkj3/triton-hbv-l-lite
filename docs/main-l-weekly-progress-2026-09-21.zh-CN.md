# 主L周报：收益覆盖扩大，后端响应判断仍是主要瓶颈

统计范围：2026年9月14日至21日；测量截止9月21日05:19:46（世界标准时间）。本次重写只调整总结方式，未增加测试、修改模型或更改统计口径。[上周周报](main-l-weekly-progress-2026-09-13.zh-CN.md)保留供对照。

本周的主要成果，是把一批原先进不了预测、或被模型低估的优化方案变成实际收益。旧L-lite的228个物质收益机会，主L从找回27个增加到94个：**原有27个全部保留，新增67个**。但扩大选择范围后，也暴露出61个减速选择。当前已不是单纯“能不能生成候选”的问题，而是必须进一步判断：同一种代码变换，在不同资源与工作量条件下，究竟会加速还是减速。

这里的“入口”指一个算子在特定输入和编译配置下的实例；295个入口并非295种算子。“物质收益”沿用至少1.0175倍加速的门槛。“收益恢复率”按主L所选方案的实测加速比除以L-lite历史最佳加速比计算。例如历史最佳2倍、主L1.8倍，恢复率为90%。

# 一、收益变化：保住27个旧成果，新增67个，但选择可靠性还未达标

## 1.1 收益机会明显增加，不能据此认为模型已经稳定

|指标|本周迁移后第一轮全量|本周最新全量|变化说明|
|---|---:|---:|---|
|测试入口总数|295|295|固定总范围|
|找回历史物质收益机会|27/228，11.8%|94/228，41.2%|旧27个全部保留，新增67个|
|预先选择优化方案|34|189|更多候选进入实际选择|
|正确并完成计时|280|274|本轮有8个所选候选资源超限，不能忽略|
|正确计时入口中，恢复率达到90%|177/280，63.2%|179/274，65.3%|改善远小于机会覆盖的增长|
|正确计时入口中，恢复率达到95%|139/280，49.6%|145/274，52.9%|仍有明显差距|
|所选优化比原程序慢|7|61|扩大采用范围也带来更多误选|

两轮候选实现、模型和测量时点均发生变化，表格说明整体开发结果，不能把新增67个机会全部归功于某一次模型修正。

这组结果有两层含义。第一，原先大量放弃优化的问题有所缓解，工程和模型修复确实找回了收益。第二，模型还没有稳定区分“值得优化”和“优化后反而更慢”的状态；采用数量增加得很快，90%恢复达标比例却只小幅上升。下一步不能继续仅以增加采用数作为进展。

本轮189个优化选择中，175个正确计时：99个达到物质收益门槛，15个只有小幅正收益或持平，61个减速。99个有收益的选择中，94个属于旧L-lite的228个机会，另5个来自历史未达物质收益门槛的入口，单独记账。

## 1.2 重排、向量化、软件流水都有收益，不是只做了其中一种

Bridge（构造循环）仍然是前置步骤；完全展开＋重排、完全展开＋向量化、软件流水是面对循环的同级选择。下面按执行路径统计结果，不代表把六个组合做成六套专用模型。

|是否先构造循环|后续优化|预先选择数|正确计时数|物质收益数|
|---|---|---:|---:|---:|
|否|完全展开＋重排|29|26|23|
|是|完全展开＋重排|27|27|18|
|否|完全展开＋向量化|10|9|6|
|是|完全展开＋向量化|19|19|9|
|否|软件流水|63|56|35|
|是|软件流水|41|38|8|

重排合计贡献41个物质收益选择，向量化15个，软件流水43个。这里统计的是本轮被选中的方案，不是各条路径的全部候选覆盖率，也不能由此断言一种优化普遍优于另一种。

有代表性的结果包括：261号归一化反向计算约2.266倍、233号约2.204倍、276号三角矩阵处理约1.340倍。反面例子同样明显：160号二分查找只有约0.559倍、157号约0.577倍。这些大幅减速不能用测量噪声解释。

## 1.3 相对上周：证据从局部成功扩大到了统一选择

上周向量化局部测试中，27/28个物质收益机会达到90%恢复；软件流水局部测试中，53/54达到90%。这些成绩证明了局部方法可行，但不等于把所有优化放到一起后仍能选对。

本周统一选择暴露出的主要差距，正是局部测试难以揭示的误选和跨状态迁移问题。因此不能拿上周局部接近100%的比例，与本周全量65.3%直接比较，得出“项目整体退化”的结论。相同历史机会范围内，实际找回数从27增加到94；更广的选择质量仍不够稳定。

核心验收目前尚未达到：在历史228个物质收益机会中，122个已确认达到90%恢复，92个达到95%。这与“94个真正重新取得物质收益”是两个指标——保留原程序也可能接近一个只有小幅优化空间的最佳方案。

# 二、具体工作：分别修复信息缺失、响应学习和测试接线

## 2.1 补齐状态传播，让模型看到循环实际做了多少工作

**问题。** 循环中的读取、写入可能位于辅助函数或分支内部。如果只数循环表面的操作，就会把“通过函数调用完成的读写”漏掉。优化方案虽然能生成，预测模型收到的却是不完整工作量。

**本周修改。** 补充可见函数体的工作量汇总、调用参数范围、循环变量范围和完整循环体摘要。保留两类不同信息：循环表面直接包含什么操作，以及展开可见结构后实际包含多少工作。未知信息仍标为未知，不填成零。

**实际作用。** 276号入口新增12条可预测候选，全部通过物化（实际生成目标代码）、后端编译和正确性检查，局部实测达到1.138—1.369倍。相关89项测试通过。

这项修复解决的是“模型看不见候选工作”，不是直接解决时间预测。修复之初，模型仍把这些有收益候选全部预测为减速，随后才继续定位响应学习问题。

## 2.2 保留独立响应模型，补足不同工作量下的学习依据

**问题。** 模型有程序数量等输入，不等于已经学会这些量与耗时之间的关系。276号入口在不同批量下出现收益方向反转，原模型没有正确描述这种变化。

**本周修改。** 在保留独立模型的基础上，补充16批和512批的24条开发观测，不按算子名、Bridge来源增加专用模型。随后检查已知反例，并先固定预测，再执行新的64批、256批测试。

**实际作用。** 128批的局部收益恢复从保留原程序时约73.5%，提高到97.51%；新测64批和256批分别达到100%和99.08%。旧107入口的同口径总体指标没有下降。

**没有解决的部分。** 64批的预测加速比仍高估约18%—38%；推广到另一个入口277后，模型预测约1.277倍，实测却约0.989倍。因此当前成果是局部响应学习得到改善，不是跨算子泛化已经完成。[修复与验证依据](evidence/weekly-2026-09-21/supply-supervision-repair-review-v1.md)。

## 2.3 提纯实现，减少旧入口和隐含名单对能力的限制

本周将候选生成、合法性判断、代码转换、状态传播和Python预测实现向l_core（项目核心实现目录）集中，外部Triton、LLVM、CUDA安装仍作为环境依赖，不搬进项目核心。

同时拆清循环发现、地址范围、分支工作量、嵌套结构和向量组装等公共职责；部分操作名单判断改为依据操作语义和依赖规则。阶段性CPU回归达到429项通过。

这项工作的收益主要是减少错误绑定和后续返工，不能单独算成某个加速比。完整独立交付及与L-lite共享能力的最终同步仍需核验，不能因为代码已经提纯就宣称全部完成。

## 2.4 修复测试接线，避免把未执行误报为优化失败

本轮全量暴露了两类普通工程错误：测试程序要求新代码保留旧参数名；已有测试实现未接入全量入口。已按参数位置和类型重新绑定，并接回漏掉的入口，没有修改候选、模型、输入要求或计时方法。

56项补测中，50项正确并计时，6项仍未通过原程序参考检查。接线错误已经解决，不能继续列为预测能力缺口；原程序参考失败则需要另行归因，不能靠放宽正确性要求消除。

全量与补测合计25分50秒。上述开发任务未单独记录工时，不用提交时间跨度充当人工工时。这25分50秒包含测试准备、正确性检查和重复计时，也不是主L正式搜索开销；本周尚未完成与当前L-lite全流程费用的严格对照。

# 三、新增细节与潜在创新：哪些是研究贡献，哪些只是应有的工程修理

## 3.1 把“代码变换”与“后端时间响应”分开表达

本周进一步确认，优化名称不能直接决定时间模型。Bridge负责构造循环，三个同级优化负责改变循环；预测要消费这些变换造成的状态变化，而不是把“构造循环＋重排”当成一种固定快慢属性。

在276号入口的六对重排／向量化候选中，五对最终机器指令相同。这说明两个不同的上游转换可能得到同一种执行结果。模型若仅因转换名称不同就预测出不同后端成本，可能人为制造差异。

**可形成的贡献**是：让多步骤候选搜索通过明确状态交接，统一落到有依据的后端响应表达上。**目前还不能声称的成果**是：所有响应状态已经识别，或已经形成可跨架构直接复用的统一模型。

## 3.2 从“每块资源”扩展到“每块工作＋整次启动的工作供给”

过去容易把寄存器数、单块工作量等局部量当作主要判断依据。本周固定机器码改变批量的实验说明：每块资源不变，收益仍可以由负转正，整次启动的工作量与可调度线程块数量必须一起解释。

新增价值不在于“发现批量会影响性能”——这本身不能宣称新颖。值得继续提炼的是：如何从编译前可见状态推导这些量，如何为候选选择建立可验证的时间响应，而不依赖逐个候选实测取得参数。

目前已得到具体反例和局部学习改善，但完整通用公式尚未建立。这是有证据支撑的研究方向，不是已经完成的论文创新结论。

## 3.3 补信息时区分“原本看得见但丢了”与“后端确实不可见”

函数体工作量、循环范围和部分掩码关系，本来就存在于可见代码中。把它们补进传播链，是恢复已有事实，不是凭空推测硬件状态。

这一区分影响论文归因：如果误差来自信息在模块间丢失，应归为工程或状态表达缺口；不能把它放入环境残差，更不能提前推到项目边界之外。只有保留这些信息仍不足以解释的部分，才需要统计代理及相应的不确定性处理。

|本周新增内容|当前定位|距离论文贡献还缺什么|
|---|---|---|
|跨函数与结构化循环的完整工作量传播|已实现并验证的项目能力|进一步证明覆盖范围与必要性，不宣称原生编译器普遍缺少这些信息|
|候选变换与后端响应分离|架构方向及局部证据|完整响应划分、跨对象验证|
|工作供给与每块服务联合解释|实验支持的建模方向|从预编译状态预测参数，验证迁移|
|参数绑定、测试入口修复|普通工程修理|不包装成算法创新|
|少量批次补监督恢复选择|局部模型改进|数值校准和独立对象验证|

# 四、新发现的后端依赖关系：已有定量证据，但不能越过证据下结论

这里的“新发现”指本周在本项目中查明或进一步缩小的关系，不表示首次发现于业界。每项分别说明变化链、已有证据和模型应如何使用。

## 4.1 构造循环改变的是工作分配，不一定改变总有效读写量

276号入口处理64×64的单精度矩阵，每个原始程序处理两行，按条件只读取三角区域，同时写出整个矩阵。

对一张矩阵：

```text
有效读取元素数 = 1 + 2 + … + 64 = 2080
写出元素数     = 64 × 64        = 4096
128批有效读取  = 2080 × 4字节 × 128 = 1,064,960字节
128批写出      = 4096 × 4字节 × 128 = 2,097,152字节
```

Bridge把多个逻辑程序组织到一个循环中，保持上述总量，改变每个程序承担的工作和物理程序数量。原程序128批共有4096个程序；构造系数为2、4、8时，分别变成2048、1024、512个，每个程序负责的工作增加。

可确认的变化链是：

```text
构造系数增大
  → 每个物理程序合并更多逻辑工作
  → 单程序工作量增加、物理程序数减少
  → 并行供给和每程序执行成本发生变化
  → 总耗时需要综合判断，不能预设一定加速
```

注意：有效元素对应的字节数，不等于实际显存事务量。缓存、访问合并等仍可能改变硬件流量。本例关系是对实际代码的诊断推导，尚未全部变成通用自动提取规则。[推导与实验](evidence/weekly-2026-09-21/response-276-batch-review-v1.md)。

## 4.2 单块资源相同，整次启动的工作量变化仍能翻转收益

保持276号入口的机器码、矩阵大小、数据类型和候选参数不变，只改变独立批次数：

|构造系数／重排参数|16批|128批|512批|
|---|---:|---:|---:|
|2／2|1.055倍|1.327倍|1.687倍|
|4／2|0.917倍|1.360倍|1.769倍|
|8／2|0.667倍|1.136倍|1.705倍|

36次正确性检查全部通过。特别是最后一行，同一候选从明显减速变为明显加速，不能用“这条转换本来就慢”解释。

批量增加同时增加总工作量、可调度程序数和数据工作集。因此已证明的是：**仅凭每块资源不足以决定收益方向**。还没有单独证明是调度、缓存或某一硬件单元造成了全部变化，不能把多个同时变化的因素硬说成一个原因。

探索性地用两端批量拟合：

```text
T(B) = a + b × B
B：批次数；T：执行时间
a：拟合截距；b：该固定程序在此范围内的增长斜率
```

对中间128批，12个候选的时间误差约为−3.61%至+6.72%。这支持进一步区分固定部分与随工作量增长的部分。但a不能直接叫启动延迟，b不能直接叫带宽倒数；该拟合用了每个候选的实测，尚不是低搜索开销的部署方案。

## 4.3 寄存器增加，不等于驻留数量下降，更不等于发生溢出

276号原程序使用16个寄存器，候选为19—34个；但查询到的理论驻留上限均为每个计算单元24个线程块，也没有观察到寄存器溢出访问。

因此，本例不能使用下面这个未经验证的捷径：

```text
寄存器增加 → 并行度必然下降 → 必然减速
```

需要核验的实际链条是：

```text
活跃值及后端分配变化
  → 寄存器占用变化
  → 是否触及分配、驻留或溢出限制
  → 是否改变当前主要耗时来源
```

本例证据排除了“仅由寄存器增加就判减速”的解释，并未证明寄存器变化永远没有成本，也没有把理论驻留上限当作实测运行占用率。

模型上的要求是：保留资源变化，但不能给所有寄存器增加统一附加减速。后编译资源查询用于开发监督，不能伪装成预测前免费的输入。

[资源与最终机器指令核查依据](evidence/weekly-2026-09-21/response-276-paired-review-v1.md)。

## 4.4 模型分类越过边界，不代表硬件性能也越过边界

对构造系数2的候选，192批对应3072个线程块，193批对应3088个。当前分类规则在这一点从“容量关系尚不确定”切换到另一个模型，导致：

|重排候选|192批|193批|
|---|---:|---:|
|模型预测加速|0.6573倍|1.0964倍|
|实际测量加速|1.4500倍|1.4363倍|

输入总量只增加约0.52%，预测却上升约66.8%；实测没有支持这种大幅跳变。重排和向量化共4次边界检查均通过正确性。

这里找到的是一个**模型内部分组错误的反例**：关于资源的知识是否充分，与硬件执行机制是否变化，不是一件事。前者可以作为诊断标签，但不能直接决定切换另一套时间系数。

删除所有模型分组也不是答案。共享模型的对照改善少量入口，却损伤其他入口，且未解决276的整体低估；没有部署。应保留有依据的响应差异，重新验证分类条件，而不是为了消除一处跳变强行合并所有模型。[边界证据](evidence/weekly-2026-09-21/response-276-dispatch-boundary-review-v1.md)。

## 4.5 软件流水的共享内存需求，必须落到最终缓冲规划上

最新全量有8个所选候选因共享内存超限不能执行。例如33号候选实际需要114,688字节，而当前设备该执行路径的上限为101,376字节。这是明确的容量冲突，不是计时误差。

需要继续补齐的链条是：

```text
循环的数据、布局与请求流水阶段数
  → 后端形成的缓冲区及其存活关系
  → 实际共享内存需求
  → 是否满足设备执行上限
```

本周已补充源缓冲状态表达，但这8项结果说明预测与可执行性判断还不完整。当前只能确认资源超限事实，尚不能把“阶段数乘某个数据大小”当作已验证的通用精确公式，更不能归为不可观测的硬件噪声。

# 结论：下一步重点从扩大采用转向提高选择可靠性

本周完成了三件有实际价值的事：历史收益机会由27增加到94；补上通用状态传播和运行接线缺口；把部分预测错误定位到了具体的工作供给关系和错误模型边界。没有完成的，是把这些认识稳定推广到全部响应状态，消除大幅误选，并证明完整搜索费用优势。

工程完成度仍暂估60%—70%；核心目标最终成功可能性暂估50%—70%。二者是工程研判，不是统计置信度。前者反映流程与能力的完善程度，后者还受响应建模、独立验证及搜索费用结果影响，不能用某个通过率替代。

下一轮优先处理8个资源超限选择，以及61个减速选择中影响面大的共同原因；同时继续分析未找回的收益机会。新修复以本次全量为基线做局部反馈，不再只展示成功算例，也不因某个算子困难就先归到项目边界之外。

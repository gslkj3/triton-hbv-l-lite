# 主L项目周报：打通状态传递，扩大真实测试，预测可靠性仍是主要差距

统计截至2026年9月21日05:19:46（世界标准时间）。本周统计9月14日至9月21日；
对照[上一份9月13日周报](main-l-weekly-progress-2026-09-13.zh-CN.md)。两次截止之间的
9月13日尾段如引用，单列为衔接背景，不混算本周工时。

本周有实质进展，但尚未完成核心目标。最新全量对照中，旧L-lite的228个明显收益
机会，主L找回94个；迁移后上一轮全量为27个。与此同时，仍有61个所选方案慢于
原程序，说明“更多候选能进入预测”尚未充分转化为“稳定选对候选”。
本报告既保留进展，也把这部分退化列为下一轮重点，不用局部成功代替总体成功。

阅读说明：本报告的295个“入口”，是算子在不同输入大小、数据类型和编译设置下的
295个测试实例，不是295种不同算子。一个算子可能对应多个入口。“候选”是一种
可尝试的优化写法；“物化”就是编译器确实生成了这种写法，而不只是给它贴了标签。
“明显收益”严格指至少1.0175倍加速，并不是说每一条微小收益都已排除环境波动。

项目分工始终如下，不能把组合路径误称为新的优化模块：

```text
输入代码
  → Bridge（构造循环，或不改变原代码）
  → 三种同级优化：软件流水 / 完全展开＋重排 / 完全展开＋向量化
  → 合法候选及其状态变化
      ├─ L-lite：逐个实测，再选最快的
      └─ 主L：预测各候选，选择一个，再编译、检查和测量
```

收益恢复率按“主L选中方案的实测加速比÷L-lite最佳实测加速比”计算。
例如旧版最佳2倍、主L1.8倍，就是90%。这与“找回了多少个有收益的入口”是两回事。
若最佳仅1.03倍，主L保持原程序也能达到97.1%恢复，但它没有真正实现优化。

# 一、从局部成绩走向全量检查，避免把几个成功例子当成全项目成功

## 1.1 接续上周结果——整理时间未单独计量

上周：在向量化的局部候选空间中，27/28个明显收益机会达到90%恢复，真正找回
26/28；在原生软件流水的局部空间中，53/54达到90%，真正找回44/54。
当时尚无全项目统一恢复率。这些局部结果不能与本周295个入口的总表直接相加。

本周保留的迁移后全量基准：295个入口中280个正确并计时，9个参考检查未通过，
2个测试夹具内存不足，4个原程序存在已知越界而隔离。旧L-lite有228个明显收益机会，
主L实际恢复27个；280个可计时入口中177个达到90%恢复。
两项指标不同：保留原程序也可能接近一个只有小幅优化空间的最佳方案。

本周中间开发轮：194个预选候选中174个正确计时，92个达到1.0175倍门槛，
其中88个对应旧L-lite的228个机会；57个慢于原程序。此轮没有重测101个Original选择，
因此是开发轮成绩，不是完整全量替代结果，也不能把88加到27上。

## 1.2 正式周报前冻结一次全量测试——全量及接线补测合计25分50秒

冻结代码、候选生成、当前实验模型与输入清单；全量重新提取事实、预测并选择，
每入口最多编译一个优化选择，再检查正确性和性能。未采用优化的入口也安排原程序
检查；已知不安全原程序不强行执行，明确列入未完成项。
保留900秒单入口上限、最多四个编译进程的约束，本次实际顺序编译。
收益测试允许共享GPU并记录环境，不把它包装为精密独占测量或独立盲测。

本轮270/295个入口至少有一个可预测优化候选，共5081条候选得到预测值。
另有5223次组合尝试被编译规则拒绝，113次启动数量不能整除，316次仍缺预测所需信息。
这些是不同阶段的数量：可预测不等于正确执行，更不等于有收益。最终在实测前
预选189个优化方案，106个入口保留原程序；没有用本轮计时再改选第二名。

本次全量也发现测试接线错误：池化、矩阵乘和二分查找仍要求新代码保留旧参数名，
另外10个入口有现成测试实现，却没有接入全量脚本。已修正位置和类型绑定、补上入口，
使用原先选中的二进制补测；没有换候选、重新拟合或放宽正确性要求。
修复前记录保留，正式汇总使用修复后的检查结果。冻结实验模型不应成为拖延工程修复的理由。
这次补测56个入口：46个核对参数绑定，10个补上已有运行入口；50个正确并计时，
6个仍未通过原程序参考检查。首轮遍历22分34秒，补测收尾约3分17秒；取整会产生一秒差异。
这是整套评价的墙钟时间，包含输入准备、进程启动、正确性检查和重复计时，不能当作
主L正式使用时的搜索开销，也不能直接与旧L-lite整库测试时间相除。

# 二、Bridge与三种同级优化：补信息传递，不按算子名字增加特殊分支

## 2.1 将项目新增实现集中到l_core——9月19日起，开发工时未单独计量

原因：历史实现、模型和运行入口交叉引用，难以确认当前究竟运行哪套代码。
工作：提取候选生成、合法性、物化、状态传播和Python预测实现；明确Triton、LLVM、
CUDA等属于外部依赖，不把整套安装环境复制进项目核心。
结果：后续真实候选通过独立编译工具物化，再使用指定的原生后端编译；不能据此
宣称所有安装与L-lite同步已经完成。最新修改仍有同步和统一交付工作。

提纯还包括把循环发现、地址范围、分支工作量、循环嵌套关系和向量组装等公共能力
拆成明确负责的实现，移除部分依赖旧入口或固定操作名单的判断。例如，能否把一组
操作一起处理，改由操作本身的语义性质和依赖限制判断，而不是只认可名单中的几种
操作。阶段性CPU回归达到429项通过；它证明相应接口和规则有检查，不等于429个真实
算子都获得加速。后续增加的测试属于不同范围，不与429简单相加。

## 2.2 构造循环后，不能把被函数调用包住的工作当成零——9月20日，开发工时未单独计量

Bridge只负责构造普通循环；下游仍是软件流水、完全展开加重排、完全展开加向量化
三选一。分析发现：被辅助函数或分支包住的读取/写入，可能没有传到模型输入。
修复可见函数体的工作量汇总、调用参数范围、循环变量范围及完整循环体摘要。
保留“直接操作数”和“完整循环体工作量”的不同含义；未知仍标未知，不能补零。
结果：276号真实入口新增12个可预测候选，全部物化、编译、正确性通过，实测
1.138—1.369倍。修复了“看不见”，但当时模型仍全部预测减速，说明物化不等于预测成功。
这一轮相关89项测试通过。例如循环内调用了一个会读取数据的辅助函数，旧摘要只看到
“调用”，就可能漏算读取；现在需要沿可见函数体汇总。不能确定的工作仍保留为未知。

## 2.3 重排与向量化各自承担转换责任——9月20日，开发工时未单独计量

重排补充有依据的内存访问关系和运行时条件校验，默认不凭空授予互不重叠假设。
56/57号条件重排已能生成相应操作顺序，但局部测量没有明显收益，运行时校验成本
也需要计入，不能只展示指令顺序改善。
276的六对重排/向量化候选中，五对最终机器指令相同。两个pass仍是不同转换，
但模型不能仅按转换名称断言后端性能不同。

## 2.4 软件流水：补齐缓冲区状态，保留资源超限的失败——9月20日，开发工时未单独计量

通过源状态推导条件缓冲工作，而不是用请求的流水阶段数直接冒充最终硬件占用。
完整开发反馈仍有容量启动失败、误选和减速。这些是待修问题，不能由“流水机制存在”
推导为所有循环都适用，也不能为Bridge另造专用流水模型。

# 三、预测体系：把“模型为何错”推进到可测量的内部原因

## 3.1 区分资源增加与真正的瓶颈变化——9月20日至21日，诊断耗时未完整单独计量

276候选寄存器从16增加到19—34，但最终产物的理论驻留上限均为每个计算单元
24个线程块，也没有观察到寄存器溢出访问。不能将预测减速简单解释为寄存器变多。
同一机器码仅改变独立批次数，某候选从0.667倍变为1.705倍；每块资源相同，
整体供应不同，收益方向可以相反。

## 3.2 找到人工模型边界引起的跳变——9月20日，诊断耗时未单独完整计量

批次192变193，预测从0.657倍跳到1.096倍，实际却从1.450倍变1.436倍。
原因是“容量是否能唯一判断”的分类切换了两个模型，并没有对应的性能突变证据。
去掉这种硬分派的对照改善少量入口，却损伤其他入口，也未修好276；未部署。
四次边界正确性检查均通过。这个结果的价值在于，把问题从“硬件可能不可预测”缩小为
“当前模型的分组条件没有得到性能证据支持”。下一步应修分组和服务关系，不是放宽验收。

## 3.3 补充响应变化监督后，局部选择改善，但不能声称已经泛化——9月20日，开发工时未单独计量

仅用16和512批的开发数据补充监督，128批未进入此次拟合，收益恢复97.51%。
随后先冻结预测，再测64和256批，恢复100%与99.08%；旧107入口总体指标不变。
但是64批的加速比数值仍高估约18%—38%，不能用选对掩盖预测偏差。
放回295入口重放后有32个选择改变，32条预选候选全部物化编译成功；新增选择的
256/277实测均约0.989倍，没有明显收益。这一负结果说明相邻入口迁移仍不可靠。

暴露出较多跨状态误选、资源超限和模型分组依据不足。评价范围变完整了。

仍然值得继续的依据是：修复通用状态传播后，确实出现可执行且有收益的候选；

特别是276改善未能自然迁移到277，本轮277仍约0.989倍，这是尚待解释的反例。

# 五、下周按共同原因修复，而不是继续堆局部成功例子

## 5.1 先处理影响范围大的明确问题——计划项，不计入本周完成量

第一，处理8个共享内存超限选择，追查资源需求从候选状态到可执行性判断的传播，
不能等到执行失败才发现；这与给Bridge单独建模型无关。

第二，对61个减速选择和仍漏掉的历史收益入口，比较原程序与所选候选的输入状态、
资源变化、机器指令和时间变化。优先研究覆盖多个入口的共同关系，必要时划分有
证据支持的后端响应模型；不按算子名字、构造来源或未见过的参数直接拒绝。

第三，修复后及时做局部反馈，进度统一挂在本次全量结果下。下一次全量再重置
局部累计，避免重复计算成绩。共享编译能力的变更同步到L-lite，预测模型不混入L-lite。

## 5.2 论文证据还缺什么——计划项，不计入本周完成量

当前历史收益入口允许用作开发集，所以本报告不能证明未见算子的泛化。
后续需要在模型与选择规则固定后验证未参与拟合的输入，并把“输入状态→后端响应
→耗时→最终选择”的推导连起来。已有文献只能支撑机制假设，不能替代本地证据。

主L与旧L-lite的输入探测值、部分候选和测量时间尚非完全一致；1个广播入口还存在
历史输入解释歧义。本次按用户要求先做开发对照，不能把它升格为严格论文结论。
若恢复率超过100%，也不能据此断言主L超过同候选空间下的完整自动调优。

只有证据足以排除内部状态丢失、错误分组、监督不足和测试接线问题后，才能把剩余
误差归到项目能力边界之外。目前这些重点失败尚不满足这个条件。
